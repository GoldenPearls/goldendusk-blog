# 2. 개요

## 🍇 프로젝트 목적 및 가치 강조

젊은 세대를 위한 행사 정보 및 대학교 축제 후기를 제공하는 이 웹 페이지는 20~30대의 여가 시간을 유익하고 즐겁게 활용할 수 있도록 합니다. 더 나아가, 사회적 문제에 대한 인식을 높이고 긍정적인 변화를 이끌어내는데 기여하는 것을 목표로 합니다.

## 🍇 정보의 접근성

현재 서울에서 열리는 다양한 축제와 이벤트에 대한 정보가 분산되어 있어 찾기 어렵습니다.
이러한 문제를 해결하고 사용자가 필요한 정보를 빠르고 쉽게 찾을 수 있도록 합니다.

## 🍇 문화 활동 증진

서울은 그 자체로 큰 문화적 중심지입니다.
하지만 많은 사람들이 어떤 종류의 축제나 이벤트가 있는지 알지 못하며,
그로 인해 많은 기회를 놓치게 됩니다. 우리의 웹사이트는 사람들이 새로운 경험을 할 수 있도록 하고 문화 활동을 증진시킵니다.

## 🍇 관광 유도

관광객들은 종종 현지의 축제나 이벤트에 참여하여 진짜 지역 문화를 체험하려 합니다.
국내외 관광객들에게 얻을 수 있는 최신 및 신뢰할 수 있는 정보를 제공함으로써 서울 방문을 더 매력적으로 만듭니다.

## 🍇 디지털 최신화

디지털 시대에 우리는 모든 것을 온라인에서 찾으려 합니다.
저희가 만드는 홈페이지는 디지털 화 추세에 맞춰 서울의 문화적 행사를 더 넓게 알릴 수 있는 효과적인 방법을 제공합니다.

## 🍇 20~30대의 스트레스 해소

요즘 시대에서는 20~30대들이 다양한 스트레스와 압박을 겪고 있으며, 이로 인해 높은 자살율이 보고되고 있습니다. 이 프로젝트는 이러한 사회적 문제에 대한 관심을 높이고, 여가 활동을 통해 스트레스를 해소하고 긍정적인 마인드를 유지하는데 도움을 주고자 합니다.

# 1차 멘토링 전 준비 기간
## 1. 피그마 작업(9월 6일 ~9월 9일)
### 진행 과정
1. 나랑 조장이랑 같이 작업 틀을 요구사항 정의서를 보고 어느정도 만들어두었다.
2. 그 후 작업 상황에 대해 공유 및 브리핑하며 괜찮은지 물어본다.
3. 그 각자 역할 분담한 곳의 디자인에 대해 의견 차이가 있어 나랑 조장이 만들어둔 피그마를 기반으로 역할 분담해서 **맡은 부분이 같은 사람들끼리 논의해서 기능적인 부분을 추가**해서 피그마를 각자 수정하기로 하였다.
### 피그마 링크
[피그마 링크](https://www.figma.com/file/TXbT2gkAER46LdABssOK0A/%EC%9E%91%EC%97%85-%ED%99%94%EB%A9%B4?type=design&node-id=0-1&mode=design&t=oO6mmh3hscrHhGNX-0)

## 2. WBS 문서 작성
### 진행과정
1. 먼저 맨 처음 WBS 작성시에는 나와 조장의 경우 피그마 작업을 진행중이었어서 나머지 팀원분들께서 초안을 작성해주셨다.
2. 그 후 같은 부분 사람들끼리 논의해서 ver1 wbs 문서 작성


## 3. 세세하게 보완
1. 그 후에 같은 부분을 맡은 사람들끼리 모여 논의하고 세세하게 좀 더 보완 
**- 로그아웃 버튼을 메인페이지 둘 것인가 마이페이지에 둘 것인가**
일단 마이페이로 결정이 났는데 블로그 글 보면서 생각이 났다.. 이 부분은 빼야 한다 메인페이지 상단바로...
**- 소셜 로그인 기능을 넣을 건인가**
강사님이 구글보다 카카오를 넣길 원하셔서 카카오를 넣기로 일단 결정했는데 멘토링 때 물어볼 거는 카카오로그인 시 프로필이나 정보등은 어떻게 받느냐..
- 관심사 조사를 회원가입 안에 넣을 것인가 완료 후 넣을 것인가..?
이 부분은 원래 다들 안에다 넣길 바라길래 그렇게 하기로 결정했다.
**그러나 추가적으로 블로그 쓰다가 생각났는데 우리 관심사 조사는 따로 빼는 게 맞다 우리는 소셜 로그인도 들어가는데 그럼 소셜 로그인 쓰는 사람들은 뭘로 가져올 건데.. 이거 논의해야 겠다.**
**- API는 무엇을 쓸 것인가 **
> **문제상황**
=> 카테고리가 분류가 되어 있어야 관심사 조사시 조금 더 편할 것 같다. 안그러면 행사/축제 소개 페이지 사람들의 부담이 커져버림
=> 하지만 여기서 문제가 발생 원래 생각하고 있던 API는 카테고리 분류가 안되어 있는 것 
=> 새로운 API 찾는 중
대안 1. 서울 분류 api : [서울 축제 행사 api](ttp://data.seoul.go.kr/dataList/OA-15486/S/1/datasetView.d)
대안 2. 인천 분류 api : [인천 축제 행사 api](http://data.seoul.go.kr/dataList/OA-15486/S/1/datasetView.d)
**- 인증은 뭘로 할 것인가**
휴대폰 인증은 유료이기 때문에 무료인 `이메일 인증`으로 바꾸기로 결정
관련 참고 링크 : [이메일 인증 구현](https://hyunipad.tistory.com/101)
**- 마이페이지 밑단에 보여주는 건 어떤게 좋을까?**
내가 쓴 글, 좋아요 한 동영상, 축제/ 행사 좋아요 한 것

# 작성하게 된 계기
> 학교에서는 주로.. 개인프로젝트가 많았고 팀 단위 프로젝트를 제대로 하는 것은 처음이었고 대부분의 팀원들이 그랬기 때문에 나 자신이 공부하면서 다른 팀원들한테도 공유할 겸 작성하게 되었다.

# 1. 의문점

## 🧐 흠… 우리는 팀프로젝트 작업을 해야하는데 돌아가는 코드는 로컬(내 컴퓨터에서) 톰캣으로 한다고 해도 데이터베이스는 공유해야 하는데 이걸 어떻게 해야할까..?

> 팀 프로젝트를 진행할 때 데이터베이스를 어떻게 공유하고 사용하는지에 대한 몇 가지 옵션이 있습니다. 데이터베이스를 공유하려**면 팀원들 간에 데이터베이스 접근 권한 및 연결 정보를 공유**해야 합니다. 일반적으로 다음과 같은 방법을 사용합니다:

1. **공용 데이터베이스 서버 사용 (온프레미스 또는 클라우드)**:
    - **AWS RDS (Amazon Relational Database Service)**: AWS RDS를 사용하여 공용 데이터베이스를 호스팅할 수 있습니다. 팀원들은 AWS RDS 인스턴스에 액세스 권한을 부여받아 데이터베이스에 접근할 수 있습니다.
    - **로컬 데이터베이스**: 팀원 중 하나가 로컬 데이터베이스를 호스팅하고 다른 팀원들에게 접근 권한을 부여할 수 있습니다. 이 경우, 데이터베이스 호스트 및 포트 정보를 공유해야 합니다.
2. **데이터베이스 백업 및 동기화**:
    - 데이터베이스의 백업과 동기화를 통해 팀원 간에 데이터 일관성을 유지할 수 있습니다. 주기적으로 데이터베이스를 백업하고 백업 파일을 팀원들에게 전달하여 데이터 손실을 방지합니다.
3. **환경 변수 및 보안 설정**:
    - 데이터베이스 연결 정보와 비밀번호와 같은 민감한 정보는 환경 변수나 비밀 관리 도구를 사용하여 안전하게 관리해야 합니다. 이를 통해 보안을 유지하고 데이터베이스 액세스를 보호할 수 있습니다.
4. **API 및 데이터베이스 엔드포인트 정의**:
    - 백엔드 개발자는 데이터베이스와 상호 작용하기 위한 API 엔드포인트를 정의해야 합니다. 이 엔드포인트를 사용하여 프론트엔드에서 데이터베이스에 액세스할 수 있습니다.

# 2.  두 가지의 사용방법

### 🧐 AWS RDS (Amazon Relational Database Service) 사용하는 방법

**1. AWS 계정 생성 및 로그인:**

AWS 계정이 없는 경우 **[AWS 웹 사이트](https://aws.amazon.com/)**에서 계정을 생성하고 로그인합니다.

**2. AWS 콘솔에 로그인:**

AWS 계정으로 로그인한 후 AWS 관리 콘솔에 액세스합니다.

**3. RDS 대시보드로 이동:**

AWS 콘솔에서 "RDS"를 검색하거나, "데이터베이스" 항목을 클릭하여 RDS 대시보드로 이동합니다.

**4. 데이터베이스 인스턴스 생성:**

- "데이터베이스 인스턴스 생성" 버튼을 클릭하여 새로운 데이터베이스 인스턴스를 생성합니다.
- "엔진 옵션"에서 MySQL 또는 원하는 관계형 데이터베이스 엔진을 선택합니다.
- "프리 티어 사용" 옵션을 선택하면 무료 티어에서 데이터베이스 인스턴스를 생성할 수 있습니다.

**5. 인스턴스 설정 구성:**

- "인스턴스 식별자" 및 "마스터 사용자 이름"을 설정합니다. 이것은 데이터베이스 인스턴스에 대한 고유한 이름과 마스터 사용자의 이름입니다.
- "마스터 암호"를 생성하고 안전하게 보관하세요.

**6. 데이터베이스 설정 구성:**

- "데이터베이스 이름"을 지정하고 필요한 설정을 구성합니다.
- "퍼블릭 액세스 가능성"을 제어하고 필요한 경우 VPC(Virtual Private Cloud) 설정을 구성합니다.

**7. 보안 그룹 및 VPC 설정:**

- 데이터베이스 인스턴스에 대한 보안 그룹 및 VPC 설정을 구성하여 액세스 제어를 설정합니다. 보안 그룹을 통해 특정 IP 주소나 범위에서만 데이터베이스에 액세스할 수 있도록 할 수 있습니다.

**8. 추가 구성 및 옵션 설정:**

- 필요한 경우 데이터베이스 인스턴스의 추가 구성 및 옵션을 설정합니다. 이 단계에서는 데이터베이스 인스턴스의 성능 및 백업 설정 등을 구성할 수 있습니다.

**9. 인스턴스 생성 및 대기:**

- 설정을 완료하면 "인스턴스 생성" 또는 "시작" 버튼을 클릭하여 데이터베이스 인스턴스를 생성하고 대기합니다. 이 과정은 몇 분 정도 걸릴 수 있습니다.

**10. 연결 정보 확인:**

- 데이터베이스 인스턴스가 생성되면 해당 인스턴스의 연결 정보를 확인할 수 있습니다. 이 정보에는 엔드포인트 주소, 포트 번호, 마스터 사용자 이름 등이 포함됩니다.

**11. 데이터베이스에 연결:**

- 데이터베이스 클라이언트 도구 또는 프로그래밍 언어를 사용하여 데이터베이스에 연결합니다. 연결 정보를 사용하여 데이터베이스에 접속할 수 있습니다.

**12. 데이터베이스 사용:**

- 이제 데이터베이스에 연결되었으므로 테이블을 생성하고 데이터를 삽입, 조회, 수정, 삭제 등의 작업을 수행할 수 있습니다.

위 단계를 따라 AWS RDS를 사용하여 MySQL 또는 다른 관계형 데이터베이스를 생성하고 관리할 수 있습니다. 보안 및 성능 관리를 위해 AWS RDS의 다양한 설정 및 옵션을 활용할 수 있습니다. 필요에 따라 데이터베이스 백업 및 복원을 설정하여 데이터의 안전성을 유지할 수도 있습니다.

### 🧐 로컬 데이터베이스 사용 방법

def reactDir = "$projectDir/src/main/frontend";

sourceSets{
    main{

        }
    }

processResources{
    dependsOn "copyReactBuildFiles"
}

task installReact(type:Exec){
    workingDir "$reactDir"
    inputs.dir "$reactDir"
    group = BasePlugin.BUILD_GROUP

    if(System.getProperty('os.name').toLowerCase(Locale.ROOT).contains('windows')){
        commandLine "npm.cmd", "audit", "fix"
        commandLine 'npm.cmd', 'install'
    }else{
        commandLine "npm", "audit", "fix"
        commandLine 'npm', 'install'
    }
}

task buildReact(type:Exec){
    dependsOn "installReact"
    workingDir "$reactDir"
    inputs.dir "$reactDir"
    group = BasePlugin.BUILD_GROUP

    if(System.getProperty('os.name').toLowerCase(Locale.ROOT).contains('windows')){
        commandLine "npm.cmd", "run-script", "build"
    }else{
        commandLine "npm", "run-script", "build"
    }
}

task copyReactBuildFiles(type:Copy){
    dependsOn "buildReact"
    from "$reactDir/build"
    into "$projectDir/src/main/resources/static"
}

# 팀 프로젝트를 위한 merge와 전체 branch 쓰는 법
## 다시 정리하는 이유
- 팀원들에게 정리해서 레퍼런스 하기 위해서 다시 간단하게 정리한 것을 블로글에 올린다.

> 관련 영상 : https://www.youtube.com/watch?v=tkkbYCajCjM&t=17s

### 1. 클론(clone)

1. 팀 프로젝트 레포지토리에 있는 main > dependency(main에서 복사해온 파일로 임시 이름) main이 아닌 `dependency`를 내 컴퓨터에 복사(클론)한다.
- `main` 이나 'master'은 최종의 최종이기 때문에 건들지 않는다(조장님이 push못하게 막아두면 push가 어차피 안될 것)
### 2. 브랜치
2. 이슈만들기나 브랜치만들기로 `파트별 브랜치`를 만든다. login이면 login festival이면 festival
3. 그 안에 `각자 작업할 브랜치`를 만든다.(같은 파트에서도 여러명으로 나누어지니까)
4. 로그인 파트 중 첫 번째 파트로 이름을 login1으로 같은 파트 맞은 분끼리 맞췄다 하면
5. 기존에 있는 것(맨 처음 클론해온 것)은 절대 삭제하지 말고 **추가하는 방식으로 패키지 관리해주면 된다.**
- 깃허브에서는 각자 패키지를 만들어서 사용하면 될 것 같다.
6. 스프링 부트의 경우 이런식

![](https://velog.velcdn.com/images/prettylee620/post/f3cc11d6-cd27-4cc1-88d2-670a835c442e/image.png)


7. 리액트의 경우도 routers나 컴포넌트에 저런 식으로 작업

![](https://velog.velcdn.com/images/prettylee620/post/eced14e5-d275-4919-846b-d37762a7b3bf/image.png)


8. 그 후 각자 작업 완성 후 같은 파트 나눈 사람들끼리 이야기를 나눈 후 `파트별 브랜치` 에 merge(병합한다.) 충돌 나는거 잘 확인
9. 충돌 나는 것을 확인 한다.
10. 잘 작동하는 지 보고 dependency에 복사한다. **main은 절대 건들이지 말 것!**
11. 마지막에 `배포`할 때 main이나 master 로 최종 마지막으로 복사한다.
